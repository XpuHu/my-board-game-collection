# GitHub Free + Vercel Hobby + Neon Free

Проект подготовлен к PostgreSQL. Рабочий `dev.db` и существующий `.env` при
подготовке не изменяются. Старый `DATABASE_URL=file:...` больше не подходит
для запуска этой версии: сначала настройте PostgreSQL. Для локальной проверки
Neon не нужен. Публикация, создание аккаунтов и переключение коллекции ещё
не выполнены.

## Локальная проверка без Neon

Требуется Node.js 22.20+ и зависимости из `package-lock.json`.

```powershell
npm ci
npm run db:generate
npm run test:tools
npm test
```

`npm test` самостоятельно создаёт временный PostgreSQL через PGlite, доступный
только на `127.0.0.1` и случайном порту, и закрывает его после проверки.
Рабочая SQLite и внешние базы не используются. Это PostgreSQL в WASM с
ограничениями конкурентных подключений; проверку реального Neon, его пула,
TLS, задержек и конкурентных запросов нужно отдельно пройти перед переездом.

Для ручной проверки владелец может запустить постоянную локальную базу:

```powershell
npm run db:local
```

Команда запускает только БД, печатает два URL и идентификатор цели. Оставьте
терминал открытым. В другом терминале задайте напечатанные URL; `PORT` ниже
замените реальным портом:

```powershell
$env:DATABASE_URL = 'postgresql://postgres@127.0.0.1:PORT/postgres?sslmode=disable'
$env:DATABASE_URL_UNPOOLED = $env:DATABASE_URL
npm run db:deploy -- --target '127.0.0.1:PORT/postgres'
```

Данные локального PostgreSQL сохраняются в игнорируемом `.test/local-postgres/`.
Порт может измениться при следующем запуске. Скрипт не запускает Next.js и
не редактирует `.env`. После подготовки данных запуск приложения для ручной
проверки выполняет владелец.

## Перенос SQLite в пустой PostgreSQL

1. Сохраните копию SQLite и прежний commit приложения. Для окончательного
   переезда остановите локальное редактирование и внешнюю синхронизацию.
2. Создайте согласованный полный снимок. Чтение SQLite выполняется в read-only
   транзакции; обычный JSON-экспорт интерфейса имеет другой формат.
3. Примените PostgreSQL-миграции к пустой целевой базе.
4. Перенесите снимок и проверьте результат. `TARGET` — точный идентификатор
   `host:port/database`, без имени пользователя, пароля и query-параметров.

```powershell
npm run db:snapshot -- --source dev.db --out private-backups/sqlite-final.json
npm run db:deploy -- --target 'TARGET'
npm run db:transfer -- --input private-backups/sqlite-final.json --target 'TARGET'
npm run db:verify -- --input private-backups/sqlite-final.json --target 'TARGET'
```

URL назначения берётся только из `DATABASE_URL_UNPOOLED`. Пул Neon
`*-pooler.*` для этих операций не используется. Идентификатор цели обязателен
также для seed, Prisma Studio и разработки миграций:

```powershell
npm run db:migrate -- --target 'DEVELOPMENT_TARGET' --name description
npm run db:seed -- --target 'EMPTY_DEVELOPMENT_TARGET'
npm run db:studio -- --target 'DEVELOPMENT_TARGET'
```

Не выполняйте seed перед полным переносом: системные типы также переносятся
со своими исходными ID. Перенос проверяет совпадение схемы, пустоту назначения
и целостность снимка, блокирует таблицы на время записи, сохраняет связи и
`CommandReceipt`, затем сверяет полный хеш данных внутри транзакции. При
ошибке транзакция откатывается. Повтор в заполненную БД завершается отказом
без перезаписи. Используйте новую пустую БД для повторной репетиции.

Старые SQLite-схема и миграции находятся в `prisma/sqlite-archive/` и не входят
в активную PostgreSQL-историю. SQLite `_prisma_migrations` не переносится.
PostgreSQL-история создаётся штатной командой `migrate deploy`.

## Внешняя тестовая база

По умолчанию достаточно `npm test`. Для проверки именно Neon задайте все
переменные отдельной очищаемой test-БД:

```text
TEST_DATABASE_URL=pooled PostgreSQL URL тестовой базы
TEST_DATABASE_URL_UNPOOLED=direct PostgreSQL URL той же тестовой базы
TEST_DATABASE_EXPECTED_ID=точный host:port/database из TEST_DATABASE_URL
```

Запуск через `npm test` обязателен: прямой запуск Vitest не разрешает очистку.
Launcher проверяет идентификатор, соответствие pooled/direct и отклоняет
известные development/production URL, в том числе pooled-алиас того же Neon
endpoint. В test-БД создаётся схема и очищаются пользовательские таблицы.
Указание отдельной test-БД и её точного идентификатора — обязательное условие;
эта команда предназначена для разрушительных тестовых данных.

## Настройка аккаунтов и первого размещения

Владелец выполняет следующие действия в кабинетах:

- Создаёт приватный репозиторий в личном GitHub Free и проверяет состав push.
  `.env`, SQLite, резервные копии и личная документация `docs/` в Git не входят.
- Создаёт постоянный проект Neon Free и отдельные нерабочие среды.
  Выбирает близкие регионы Neon и Vercel Functions.
- Получает pooled URL приложения и direct URL миграций; сохраняет их в
  локальной конфигурации и соответствующих средах Vercel, без отправки в чат.
- Импортирует репозиторий в Vercel Hobby. Конфигурация `vercel.json` задаёт
  `npm ci` и `npm run build:vercel`; сборка генерирует клиент и собирает Next.js,
  не выполняя миграции, seed или импорт.
- Для первого размещения использует только пустую / синтетическую БД.
- В Settings → Deployment Protection включает **Vercel Authentication**
  и **All Deployments**, включая Production. Проверяет, что настройка
  включена в Hobby без платного дополнения. Standard Protection недостаточна.
- В браузере без входа проверяет все рабочие адреса и API импорта, экспорта,
  чтения и изменения данных. Доступ разрешается только аккаунту владельца.
- После репетиции и проверки защиты переносит настоящие данные, задаёт
  Production URL и публикует проверенный commit. Preview не получает
  Production-пароли и подключается только к нерабочей базе.

`DATABASE_URL` доступен серверу приложения. `DATABASE_URL_UNPOOLED` требуется
оператору миграций и копирования; обычная сборка работает и без него. Никакие
секреты не должны иметь префикс `NEXT_PUBLIC_`.

Приложение использует защиту Vercel, своей системы аккаунтов пока нет.
Отключение Deployment Protection или перенос на другой хостинг без новой
защиты откроет API. Файл `vercel.json` сам по себе эту настройку кабинета
не включает. Личные данные нельзя публиковать до проверки защиты.

## Полные резервные копии и восстановление

Команды работают без установленного `pg_dump`: создаётся собственный полный
логический снимок всех таблиц приложения, с ID, справочниками, связями,
историей команд, числами в строковом представлении и согласованной транзакцией
чтения. Формат версионирован и защищён контрольными суммами. История миграций
PostgreSQL сохраняется как метаданные; SQL-схема восстанавливается миграциями
того же commit приложения. Это не нативный SQL dump для `pg_restore`.

```powershell
npm run db:backup -- --target 'TARGET' --out private-backups/postgres-final.json
```

Для шифрования создайте один 32-байтный случайный ключ в base64 и сохраните
его в менеджере паролей / отдельной резервной копии. Можно получить ключ через
`node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"`.
Выполняйте генерацию лично; не сохраняйте вывод с ключом в историю проекта.
Внесите ключ в `BACKUP_ENCRYPTION_KEY` локального `.env` или секрет хранилища:

```powershell
npm run db:backup -- --target 'TARGET' --out private-backups/postgres-final.json.enc --encrypted
```

Используется AES-256-GCM со случайным nonce. Существующий файл никогда не
перезаписывается; для следующего снимка задайте новое имя. При восстановлении:

1. Выберите новую пустую PostgreSQL-БД и настройте её direct URL.
2. Получите совместимый commit приложения и примените его `db:deploy`.
3. Для зашифрованного файла настройте прежний `BACKUP_ENCRYPTION_KEY`.
4. Выполните `db:transfer` и `db:verify` с файлом копии и новым TARGET.
5. Проверьте данные и вход, затем переключите приложение на восстановленную БД.

Проверка равенства с копией применима до новых записей либо к отдельной
восстановленной БД. Последующие рабочие изменения закономерно меняют хеш.
Возврат старого deployment Vercel не откатывает схему или данные PostgreSQL.
После новых записей в Neon возврат к прежней SQLite требует отдельно
сохранить и перенести новые изменения, иначе они будут потеряны.

## Автоматизация GitHub

`Project checks` запускает тесты, lint, typecheck и сборку на push в `main`,
pull request и вручную. Секреты Neon для CI не требуются: тестовая база временная.

`Encrypted collection backup` подготовлен, но **отключён до настройки**.
Чтобы включить его в приватном репозитории, создайте:

| Настройка GitHub Actions | Значение |
| --- | --- |
| Secret `NEON_BACKUP_URL` | Direct URL рабочей базы; предпочтительно отдельная роль с правами чтения |
| Secret `BACKUP_ENCRYPTION_KEY` | Сохранённый ключ шифрования копий |
| Variable `BGC_BACKUP_TARGET` | Точный host:port/database прямого подключения |
| Variable `BGC_BACKUP_ENABLED` | `true` после проверки квот и ручного успешного запуска |

Расписание — ежедневно в 02:23 UTC / 05:23 по Москве; запуск GitHub может
задерживаться. Зашифрованный артефакт хранится семь дней. Сначала выполните
ручной запуск и восстановление скачанного файла. Храните ключ отдельно от
артефакта. Проверьте бесплатные квоты Actions / хранения и настройки остановки
расходов; workflow сам не включает платный тариф. Ошибка резервирования
отображается в Actions; настройте уведомления владельца в GitHub.

## Что ещё требует облачной проверки

- Реальное подключение к Neon, TLS, pooler, холодный старт и гонки независимых подключений.
- Настройка приватного GitHub-репозитория, Vercel Hobby и All Deployments.
- Браузерная приёмка владельцем с телефона и компьютера.
- Финальный снимок на момент переключения, рабочий перенос и первое внешнее резервирование.
- Контроль актуального `npm audit`: существовавшие до переезда проблемы зависимостей учитываются отдельно; критические runtime-проблемы должны быть исправлены до публикации.
